# ADR-023：统一有界资源调度与可观测稳定性

- 状态：Accepted
- 日期：2026-08-19

## 背景

扫描器、Sidecar 指纹和缩略图解码此前分别控制工作：扫描批次使用自己的并行迭代，解码器使用独立条件变量，哈希没有进程级总量约束。即使每一处单独看似有限，任务叠加后仍可能超过合理的 CPU、磁盘和内存预算。应用退到后台时也没有统一降级语义；文件监听回调和扫描到 UI 的批次之间缺少明确的队列容量。

资源控制不能引入数据库或改变文件系统真相源。等待、超时和监控数据都只是运行期派生状态，进程重启后可从零恢复。

## 决策

1. 进程建立一个共享 `ResourceController`，把工作分为 `scan`、`hash`、`decode` 三类。每项工作同时受分类上限和全局上限约束；默认全局前台上限取可用处理器数但不超过 8，扫描与哈希分别不超过 2，解码不超过 4。
2. 等待许可的任务最多 256 项，默认等待 30 秒。队列已满、等待超时、协作取消和锁失效均返回明确错误并累计运行期计数；许可析构时必定归还容量。
3. 窗口失去焦点后切换到后台模式，将可启动工作的全局上限降为前台的一半且至少为 1。已经开始的工作允许完成，新工作等待容量收敛；重新获得焦点后恢复前台上限。
4. 正式扫描批次、元数据/事务/重联哈希和缩略图解码接入同一个控制器。扫描批内不再自行展开 Rayon 并行；多个根扫描仍可在统一扫描上限内并发。
5. 文件解析在规范化、文件信息、尺寸、原生元数据和 Sidecar 阶段之间检查取消和每文件 5 秒协作期限。单次不可中断的操作完成后立即重新检查；超过 256 MiB 的素材跳过原生元数据解析，超过 4 MiB 的 Sidecar 跳过 YAML 解析，并以 `resource-limited` 素材问题展示，不影响素材可见性。
6. 操作系统监听回调使用容量等于单批事件上限的同步通道。回调不得因消费端落后而无限堆积；队列满时丢弃新增原始提示并发出根范围 `queue-overflow` 一致性扫描请求。
7. 扫描生产者与桌面消费端之间使用每个扫描最多 8 个批次的同步通道，并要求 JavaScript 消费每个批次后按扫描 ID 与序号确认。后端最多保留 8 个未确认批次；确认停止 30 秒后扫描失败且结果不得成为权威目录。生产者在队列满时反压，UI 通道关闭时触发扫描取消。桌面进程同时最多启动 8 个扫描与 64 个根监听，连同其线程和系统句柄一起保持硬上限。
8. 后端提供只读运行期状态：前后台模式、活动/等待/峰值、完成/拒绝/超时/取消计数、活动扫描与监听数、扫描批次容量及缓存用量。前端集中登记对象 URL，逐项创建/回收并报告活动数、峰值和创建/回收账本。
9. P2-A11 使用独立 `resource-soak` 进程和 Node 监控器执行。默认生成 100,000 素材、连续运行 8 小时、反复扫描、制造文件事件、哈希和解码，并采集 RSS、CPU、线程、文件句柄、调度器与缓存曲线。短时运行只验证工具链，不替代 8 小时退出验收。

## 后果

- 扫描、哈希和解码叠加时仍有单一可解释的进程预算；
- 后台降级不需要取消已经完成一半的安全文件操作；
- 事件风暴和 UI 消费变慢只会产生反压或保守重扫，不会形成无界内存队列；
- 慢盘上的单次系统调用无法由安全 Rust 强制中止，但各阶段之间最多继续一个不可分割操作；
- 运行期指标不含素材路径、Tag、备注或其他用户元数据；
- 扫描批内改为顺序解析，单扫描峰值并行度降低；多根并发和更稳定的交互延迟由统一调度器补偿。

## 拒绝的方案

- 为扫描、哈希、解码分别保留互不知情的并发限制；
- 用无界通道吸收文件事件或 UI 批次；
- 后台运行时强制终止正在读取或原子写入的文件操作；
- 为资源计数、任务队列或稳定性曲线引入 SQLite/IndexedDB；
- 把短时 smoke test 记录为 P2-A11 的 8 小时通过证据。
